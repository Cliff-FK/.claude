# Contrôles de sécurité WordPress : point d'entrée → contrôles obligatoires

Référence partagée (écriture de code, revue, réponse à incident). Faits vérifiés dans le core 7.1.2 (`fichier:ligne` entre parenthèses) ou la doc officielle (URL). Une ligne sans preuve n'a rien à faire ici.

## 1. Matrice point d'entrée → contrôles

| Point d'entrée | Contrôles obligatoires | Pièges vérifiés |
|---|---|---|
| **REST** (`register_rest_route`) | `permission_callback` **par méthode** (GET ≠ POST/PUT/DELETE) **et par objet** (`current_user_can( 'edit_post', $id )`, pas seulement `edit_posts`) ; `args` déclarés avec `type`/`enum`/`required` ; retourner `WP_REST_Response`/`WP_Error`. | `__return_true` n'est admissible que sur une lecture publique, jamais sur une écriture (callback absent = `_doing_it_wrong` depuis 5.5, `rest-api.php:122`). **Les paramètres non déclarés ne sont ni rejetés ni nettoyés** (`sanitize_params` les saute, `class-wp-rest-request.php:852`) : ne jamais persister `get_params()`/`get_json_params()` en bloc, lister les clés. Un arg avec `type` sans `sanitize_callback` passe par `rest_parse_request_arg` = validation de schéma + sanitation (`class-wp-rest-request.php:859`, `rest-api.php:1495`) ; **surcharger `sanitize_callback` supprime cette validation**, la rétablir par `'validate_callback' => 'rest_validate_request_arg'`. `wp_send_json*()` dans un callback REST = `_doing_it_wrong` et court-circuite le serveur REST (`functions.php:4588`). |
| **REST, nonce** | Rien à ajouter dans le callback : avec l'auth par cookie, `rest_cookie_check_errors` (filtre `rest_authentication_errors`, `default-filters.php:346`) vérifie le nonce `wp_rest` **indépendamment du `permission_callback`** : nonce absent → requête traitée comme anonyme (`wp_set_current_user( 0 )`), nonce invalide → 403 (`rest-api.php:1130-1172`). | Conséquence : la protection CSRF d'une route REST repose sur un `permission_callback` qui exige un droit ; une route d'écriture en `__return_true` est ouverte à l'anonyme ET au CSRF. |
| **AJAX** (`wp_ajax_*`) | Nonce (`check_ajax_referer`) **+** capability (`current_user_can`) + contrôle par objet, indépendamment l'un de l'autre. | Nonce ≠ autorisation : il prouve l'intention, pas le droit. `wp_ajax_nopriv_*` est exécuté pour tout visiteur non connecté (`wp-admin/admin-ajax.php:195-207`) : traiter son appelant comme un attaquant. |
| **admin-post** (`admin_post_*`) | Nonce (`check_admin_referer`) + capability ; `wp_safe_redirect` en sortie. | Même logique `nopriv` pour les non connectés (`wp-admin/admin-post.php:36-58`). |
| **Options / Settings API** | `register_setting` avec `sanitize_callback` (et `type`/`show_in_rest` si exposé). `options.php` vérifie déjà `manage_options` (filtrable par `option_page_capability_{$page}`) et le nonce `{$option_page}-options` (`wp-admin/options.php:29-49, 246`). | Hors Settings API (handler AJAX/REST maison), ces contrôles n'existent pas : les écrire. Jamais de nom d'option venant de la requête (écriture d'option arbitraire). |
| **Cron** | Autoriser au moment de **planifier** ; le callback revalide ses données (objet encore existant, état attendu). | Pas d'utilisateur fiable : la loopback standard n'envoie pas de cookie (utilisateur 0), mais en `ALTERNATE_WP_CRON` le cron tourne dans la requête du visiteur (`cron.php:937-954`). Donc jamais de `current_user_can()` comme garde dans un callback cron. |
| **Uploads** | `wp_handle_upload()` / `wp_handle_sideload()` (contrôle `test_form` + `test_type` activés par défaut) ; restreindre `mimes` au besoin métier. | `test_type` appelle `wp_check_filetype_and_ext()` (vérification contenu/extension) et refuse un type inconnu sauf `unfiltered_upload` (`wp-admin/includes/file.php:918-971`) : ne jamais passer `test_type => false`. `move_uploaded_file` brut = contournement de tout ceci. |
| **HTTP sortant (SSRF)** | `wp_safe_remote_get/post/request` pour toute URL influencée par l'utilisateur. | Ils forcent `reject_unsafe_urls` (`http.php:82`) : `wp_http_validate_url` refuse loopback/privé/CGNAT et les ports hors 80/443/8080 (filtre `http_allowed_safe_ports`), et revalide chaque redirection (`class-wp-http.php:352, 529`). Limites : résolution IPv4 par `gethostbyname` au moment du contrôle (rebinding DNS non couvert), l'hôte identique à `home` est toujours accepté (`http.php:583-590`). |
| **Désérialisation** | Données externes en JSON (`wp_json_encode`/`json_decode`). `unserialize( $x, [ 'allowed_classes' => false ] )` si le format est imposé. | `maybe_unserialize()` appelle `unserialize()` sans restriction de classes sur toute chaîne sérialisée (`functions.php:653-656`) : jamais sur une donnée contrôlable (cookie, requête, meta écrite par un rôle faible) = injection d'objet. |
| **Include / chemins** | Allowlist de noms, puis `realpath()` du chemin final et vérification qu'il commence par le `realpath()` du dossier autorisé. `validate_file()` en complément (`functions.php:6372`). | Jamais d'`include`/`require` d'un chemin issu de la requête ; refuser les wrappers (`wp_is_stream()`, `functions.php:7501`), dont `phar://`. |
| **SQL** | `$wpdb->prepare()` pour toute valeur ; `%i` pour un identifiant (depuis 6.2, `class-wpdb.php:1442`) ; `$wpdb->esc_like()` puis `%s` pour un `LIKE` ; `IN()` = une liste de placeholders générée (`implode( ',', array_fill( 0, count( $ids ), '%d' ) )`) ; `ORDER BY`/colonne/sens = allowlist. | Placeholders **non quotés** : `prepare()` retire lui-même les quotes autour de `'%s'`/`"%s"` (`class-wpdb.php:1501-1502`), donc pas de double quotage, mais la forme quotée reste interdite par WPCS et fragile. |
| **Données vers JS** | `wp_add_inline_script( $handle, 'const X = ' . wp_json_encode( $data ) . ';', 'before' )` ou `wp_localize_script`. | `wp_json_encode` garde l'échappement par défaut de `/` (`</script>` → `<\/script>`, testé PHP 8.2) : ne pas lui passer `JSON_UNESCAPED_SLASHES` pour du JS inline. Jamais de concaténation de chaîne PHP dans du JS. |
| **Sortie HTML** | `esc_html`/`esc_attr`/`esc_url`/`wp_kses*` au point de sortie, selon le contexte. | `esc_html` et `esc_attr` appliquent tous deux `_wp_specialchars( ENT_QUOTES )` (`formatting.php:4753, 4778`) : la différence est l'intention et les filtres, pas les quotes. Sanitize en entrée ≠ escape en sortie. |

**Faits d'authentification** (utiles en revue, ne pas réécrire le core) : `wp_hash_password` = `password_hash()` bcrypt sur un pré-hash HMAC-SHA384, préfixé `$wp`, depuis 6.8 (`pluggable.php:2746, 2816`) ; cookie d'auth : 2 jours, 14 avec « Se souvenir de moi » (filtre `auth_cookie_expiration`, `pluggable.php:1082, 1091`). L'endpoint `block-renderer` exige `edit_post` sur le post ciblé, sinon `edit_posts` (`class-wp-rest-block-renderer-controller.php:111-129`).

**Ne jamais** « durcir » une route core en remplaçant son `permission_callback` via le filtre `rest_endpoints` : le callback core porte des contrôles fins (ex. `/wp/v2/users` réserve `context=edit`, `roles`, `capabilities`, `orderby=email` à `list_users`, `class-wp-rest-users-controller.php:202-247`) ; un remplacement par `is_user_logged_in()` les efface et ouvre ces données à tout abonné.

## 2. Durcissement wp-config / serveur

- `define( 'DISALLOW_FILE_EDIT', true );` retire `edit_themes`, `edit_plugins`, `edit_files` à tous (`capabilities.php:609` ; developer.wordpress.org/advanced-administration/security/hardening/).
- Production : `WP_DEBUG_DISPLAY` à `false` (il force `display_errors` à 1 quand il est vrai, `load.php:616`) ; la doc déconseille `WP_DEBUG` en production (developer.wordpress.org/advanced-administration/debug/debug-wordpress/). Journaliser via `WP_DEBUG_LOG`, qui accepte un chemin de fichier depuis 5.1 (`load.php:570-575`) : le placer hors de la racine servie, le défaut `wp-content/debug.log` étant servable.
- Pas de PHP exécutable dans `uploads/` : règle nginx officielle `location ~* /(?:uploads|files)/.*\.php$ { deny all; }` (developer.wordpress.org/advanced-administration/server/web-server/nginx/). Sous Apache en `.htaccess`, utiliser `<FilesMatch>` : `<Directory>` n'est valide qu'en config serveur / virtual host, jamais en `.htaccess` (httpd.apache.org/docs/2.4/mod/core.html).
- Ne pas désactiver les mises à jour automatiques de sécurité du core (`AUTOMATIC_UPDATER_DISABLED`, `WP_AUTO_UPDATE_CORE = false`) : la doc les « strongly discourage » (developer.wordpress.org/advanced-administration/upgrade/upgrading/).
- Intégrité : le core se vérifie par `wp core verify-checksums`, un plugin public par `wp plugin verify-checksums`. Un plugin ou thème premium sans référence publique se vérifie par **diff contre une copie de la MÊME version** téléchargée depuis le compte éditeur.

## 3. Méthode de revue

- **Tracer les contrôles, pas la proximité** : un nonce, un `current_user_can` ou un `prepare()` voisin ne protège que s'il gouverne le chemin atteignable ; son absence dans le même fichier ne prouve pas une faille. Suivre la donnée de l'entrée au sink.
- Nonce et capability se vérifient **séparément** sur chaque chemin qui écrit.
- **Classer avant de noter** : **Confirmé** (chemin atteignable prouvé : entrée, contrôles, sink, prérequis d'exploitation) ; **Piste non vérifiée** (hit de scan, trace incomplète) ; **Durcissement** (défense en profondeur). Seuls les Confirmés reçoivent une gravité, fondée sur impact × atteignabilité (anonyme ? rôle requis ?).
- Chaque Confirmé : `fichier:ligne`, flux de données, prérequis, impact, correctif concret, vérification exécutée (distinguée de celle seulement proposée).
- **Aucun score inventé** (pas de CVSS/CWE deviné, pas de note globale « sécurisé ») et **aucun verdict global sur un périmètre incomplet** : lister ce qui n'a pas été revu.
